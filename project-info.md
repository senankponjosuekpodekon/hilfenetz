# 54. Vision finale

L'objectif n'est donc pas de construire :

> **"un site qui présente HilfeNetz".**

Il faut construire la première version de :

> **"l'infrastructure digitale d'une plateforme de mise en relation entre offre de soutien et demande de soutien."**

La différence est importante.

L'interface publique doit déjà avoir une logique de **marketplace**, tandis que le backend doit être suffisamment structuré pour évoluer vers :

```text
                 HILFENETZ
                    │
       ┌────────────┴────────────┐
       │                         │
   DONATEURS                 DEMANDEURS
       │                         │
       ▼                         ▼
Offres de soutien          Demandes
       │                         │
       └────────────┬────────────┘
                    │
              MODÉRATION
                    │
                    ▼
               MATCHING
                    │
                    ▼
             MISE EN RELATION
```

**C'est cette architecture que je privilégierais pour le projet client : une V1 relativement simple en surface, mais avec un socle technique et UX qui ne bloque pas la transformation ultérieure en véritable plateforme.**




















Oui, **tu peux déployer une V1 de HilfeNetz uniquement sur Vercel**, à condition de concevoir l'architecture autour des services compatibles Vercel.

Pour ce projet, je ferais même une distinction entre **"Vercel uniquement"** et **"Vercel pour toute l'infrastructure applicative"**.

### Architecture V1 que je recommande

```text
                    HILFENETZ
                        │
                        ▼
                  ┌───────────┐
                  │  VERCEL   │
                  │ Next.js   │
                  └─────┬─────┘
                        │
          ┌─────────────┼─────────────┐
          │             │             │
          ▼             ▼             ▼
      PostgreSQL      Storage       Email
      (Vercel/        (Vercel       Provider
       Neon/etc.)      Blob)
```

Tu peux donc avoir :

* **Next.js** → Vercel
* **API / Server Actions** → Vercel
* **Frontend** → Vercel
* **Admin** → Vercel
* **Base PostgreSQL** → service PostgreSQL compatible
* **Fichiers/documents** → Vercel Blob ou autre stockage objet
* **Emails** → Resend, Postmark, etc.
* **DNS/CDN/HTTPS** → Vercel

Le point important : **PostgreSQL et le stockage de fichiers ne sont pas simplement "hébergés dans Vercel" comme des fichiers locaux**. Ce sont des services externes/intégrés auxquels ton application Vercel se connecte.

```text
PostgreSQL

Zod

Vercel
```

### Ce que je déconseille sur Vercel

Ne stocke **jamais** :

```text

/database.sqlite
```

directement dans le filesystem de l'application.

Pour HilfeNetz, c'est particulièrement important puisque les utilisateurs pourraient transmettre des informations personnelles et éventuellement des documents.

### Et le dashboard admin ?

Aucun problème.

Tu peux avoir :

```text

hilfenetz.com/donate

```

Le tout dans **un seul projet Next.js déployé sur Vercel**.

### Quand Vercel seul devient moins intéressant

Si tu ajoutes ensuite :

* matching très lourd ;
* traitement de documents ;
* OCR ;
* IA ;
* jobs longs ;
* scraping ;
* workers permanents ;
* WebSockets intensifs ;
* traitements asynchrones importants ;

alors je séparerais les services :

```text
                    Vercel
                      │
              Application Web
                      │
          ┌───────────┴───────────┐
          │                       │
      PostgreSQL              Backend/Workers
                                  │
                         VPS / autre cloud
```

Mais **pour la V1 de HilfeNetz, tu n'as pas besoin d'un VPS**.

Je construirais donc la première version **Vercel-first**, avec une architecture suffisamment découplée pour pouvoir sortir certaines briques plus tard sans refaire le frontend.
